# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Gladys Assistant **external integration** (Node 22+, ESM, no build step, one runtime
dependency: `@gladysassistant/integration-sdk`) for a **Withings** account: weight and body
composition, blood pressure, heart rate, SpO2, temperature, daily activity, sleep, the "in bed"
state of a Sleep Analyzer and device batteries. Gladys 5.1+ adds scene triggers, scene actions and
two dashboard widgets.

Cloud only (manifest `transports: ["cloud"]`): everything comes from the Withings public API,
through the user's own Withings developer app and the OAuth2 Connect flow relayed by Gladys.

## Commands

```bash
npm install
npm test                                    # node --test (built-in runner)
node --test test/app.test.js                # one file
node --test --test-name-pattern "Connect"   # one test by name
npm run lint                                # eslint .
npm run format:check                        # prettier --check . (CI gate)
npm run format                              # prettier --write .
npx github:GladysAssistant/integration-store .   # store admission checks
```

CI runs `format:check`, `lint`, `test` on Node 22 and 24 (plus the store checks and a Docker build
on pull requests). Releases: **Actions → Release** only (bumps `package.json`, manifest `version` +
`docker_image`, re-runs Prettier, rolls `CHANGELOG.md`, tags, builds, publishes the GitHub
Release).

## Architecture

```
index.js                   SDK bootstrap: createApp(gladys) + connect, shutdown
src/app.js                 every Gladys handler (OAuth, webhook, actions, scenes, widgets, lifecycle)
src/config.js              DEFAULT_CONFIG (mirrors the manifest) + normalization, USER_KEYS/TOKEN_KEYS
src/state.js               /data/withings-state.json: cursor, seen measure keys, last values...
src/i18n.js                LANGUAGES = en, fr, de, es; pick / localize
src/withings/client.js     Withings API: POST form, `{ status, body }` envelope -> body or WithingsError
src/withings/auth.js       authorize URL, anti-CSRF states, token manager (single-flight refresh)
src/withings/measures.js   Withings meastype -> feature key, category, unit, rounding, group kind
src/withings/sync.js       one synchronization: read, publish devices/states/events/transports
src/withings/notify.js     Gladys Plus notifications: subscribe/revoke, parse the relayed POST
src/devices/               account device (measures/activity/sleep/in bed), hardware (battery)
src/capabilities/          scene trigger keys, scene actions, widgets
```

### Invariants worth knowing

- **The refresh token rotates.** Every refresh returns a new refresh token and kills the old one:
  refreshes are single-flight, the new pair is saved (`setConfig`) before use, and the in-memory
  copy is the source of truth (a late config echo must never put a dead token back). Tokens are
  loaded from the config once per process.
- **The authorization code lives 30 seconds**: it is exchanged first thing in `onOAuthCallback`;
  the full first synchronization runs after the ack.
- **Our own `setConfig` comes back through `onConfigUpdated`**: only a change of `USER_KEYS`
  restarts anything.
- **Measures are incremental** (`getmeas lastupdate=<cursor>`), the cursor persisted in `/data`. A
  restart must never re-publish old measures (duplicate history points) nor re-fire scene events.
  First synchronization: one year read, latest value per measure published, no event.
- **Measures keep their date**: states carry `created_at` (the measure date). Current values
  (today's activity, batteries) are published without a date, through `publishChangedStates`.
- **Scene events only for what is new and recent** (< 24 h): new measurement group, new night,
  steps goal once a day, bed in/out once per change.
- **Notifications are triggers, not data** — except bed in/out (appli 50/51), which exist only as
  notifications. A notification for another Withings user is ignored. Debounced 5 s.
- **Features follow the data**: the account device gets the measures the account has (or its
  devices imply). Feature keys and external ids are forever (`gladys.externalIds('account',
userid)`, `gladys.externalIds('device', deviceid)`): never rename a key.
- **Every feature declares `min`/`max`** (NOT NULL in Gladys). Gladys has no kg/bpm/mmHg unit: those
  features are `unknown` with the unit in their name. Body temperature uses the temperature `probe`
  type so it stays out of the room average.
- **Never log** the Client secret, an access/refresh token or an authorization code.
- Trigger, action, widget, webhook and config keys are stored by users: never rename them.

### Manifest

Generated by hand, four languages everywhere (`en`, `fr`, `de`, `es`). `test/manifest.test.js`
ties it to the code: handlers, webhook, scene keys, every measure exposed as a trigger variable and
an action option, defaults = `DEFAULT_CONFIG`, every text in the four languages, version =
`package.json`, `transports` = cloud only, `gladys_version >= 5.1.0`.

## Testing

No network, no real Gladys: `createFakeGladys()` from `@gladysassistant/integration-sdk/testing`
plays Gladys, `test/helpers/fakeWithings.js` plays the Withings API (a `fetch`), and
`test/helpers/setup.js` wires them with a temporary state file, a fixed clock and manual timers.

## Conventions

- **Versions belong to the Release workflow**: never edit `version` in `package.json`, the manifest
  `version` or the `docker_image` tag by hand.
- **Changelog**: every user-visible change adds a line under `## [Unreleased]` in `CHANGELOG.md`
  (`### Added`, `Changed`, `Fixed`, `Removed`, `Security`). Never write a version heading.
- **User-facing text** is `{ en, fr, de, es }` (action messages, statuses, widgets, manifest); user
  docs in `docs/en.md`, `docs/fr.md`, `docs/de.md`, `docs/es.md`, kept in sync.
- The container rootfs is read-only: write only under `/data`.
- Prettier formats, ESLint catches mistakes. Comments explain **why**, in English.
